## ВВЕДЕНИЕ

Сфера аренды музыкальных инструментов характеризуется большим количеством операционных задач: ведение карточек инструментов, регистрация клиентов, оформление аренды, генерация договоров, прием платежей и контроль задолженностей. При ручном ведении учета (таблицы, бумажные журналы) повышается риск ошибок, потери данных и задержек в обслуживании клиентов.

Целью разработки является создание программного продукта, автоматизирующего ключевые процессы проката музыкальных инструментов: учет инвентаря, оформление и продление аренды, сопровождение договоров, прием платежей и формирование отчетности.

Объект исследования — процесс оказания услуг аренды музыкальных инструментов. Предмет исследования — методы и средства автоматизации операционной деятельности пункта проката.

Задачи работы:
1. Проанализировать предметную область и определить требования пользователей.
2. Выполнить функциональное и информационное моделирование системы.
3. Спроектировать структуру базы данных и связи сущностей.
4. Реализовать программный продукт с ролевым доступом и основными бизнес-процессами.
5. Провести тестирование и подготовить пользовательскую документацию.

## 1 Анализ предметной области и формирование требований пользователей

### 1.1 Анализ предметной области

В предметной области выделяются следующие роли:
- **Администратор** — управляет пользователями системы, имеет полный доступ ко всем функциям.
- **Менеджер проката** — работает с клиентами, инструментами, арендами, договорами и платежами.
- **Клиент** — регистрируется и заключает договор аренды.

Основные бизнес-процессы:
1. Регистрация клиента и ведение клиентской базы.
2. Добавление и актуализация карточек музыкальных инструментов.
3. Создание аренды с расчетом стоимости и депозита.
4. Автоматическое формирование записи договора аренды.
5. Прием платежей по аренде с учетом остатка долга.
6. Закрытие и продление аренды.
7. Формирование отчетов по выручке, загрузке инвентаря, должникам и активности клиентов.

Проблемы при неавтоматизированной работе:
- дублирование данных о клиентах и инструментах;
- ошибки в расчете стоимости аренды и задолженности;
- сложность контроля статусов инструментов;
- трудоемкость формирования управленческой отчетности.

Функциональные требования к системе:
- авторизация пользователей с разграничением прав;
- CRUD-операции для клиентов и инструментов;
- оформление, продление и завершение аренды;
- регистрация платежей с контролем переплат;
- хранение договоров и быстрый просмотр;
- формирование аналитических отчетов.

Нефункциональные требования:
- удобный графический интерфейс;
- устойчивость к ошибкам ввода;
- хранение данных в централизованной СУБД;
- приемлемое время отклика на операциях выборки/записи.

### 1.2 Разработка диаграммы функционального моделирования

Функциональная модель системы включает верхнеуровневый процесс **«Управление арендой музыкальных инструментов»**, который декомпозируется на подпроцессы:
- управление пользователями;
- управление инвентарем;
- управление клиентами;
- управление арендой;
- управление договорами;
- управление платежами;
- формирование отчетов.

Для визуализации функциональной декомпозиции подготовлен файл PlantUML:
- `docs/diagrams/functional_decomposition.puml`.

### 1.3 Моделирование потоков данных

Контекстная DFD-модель содержит внешние сущности:
- клиент;
- менеджер;
- администратор;
- SQL Server (хранилище данных).

Ключевые потоки данных:
- от клиента поступают регистрационные данные, заявки на аренду, платежная информация;
- менеджер инициирует операции создания/закрытия аренд и приема платежей;
- администратор управляет учетными записями сотрудников;
- система записывает и извлекает данные о клиентах, инструментах, арендах, договорах и платежах.

Для редактирования схемы в draw.io подготовлен файл:
- `docs/diagrams/dfd_context.drawio`.

### 1.4 Создание структуры входных и выходных документов

**Входные документы/формы:**
1. Форма входа в систему (логин, пароль).
2. Форма регистрации клиента.
3. Карточка инструмента (тип, бренд, модель, серийный номер, цена аренды).
4. Форма аренды (клиент, инструмент, даты, депозит).
5. Форма платежа (аренда, сумма, метод оплаты).

**Выходные документы/формы:**
1. Список активных и завершенных аренд.
2. Реестр договоров с номером и датой.
3. Отчет по доходам за период.
4. Отчет по доступности инструментов.
5. Отчет по задолженностям клиентов.
6. Отчет по клиентской активности.

### 1.5 Диаграмма вариантов использования

Система поддерживает следующие ключевые варианты использования:
- Авторизоваться в системе.
- Управлять инструментами.
- Управлять клиентами.
- Оформить аренду.
- Продлить аренду.
- Завершить аренду.
- Принять платеж.
- Просматривать договоры.
- Формировать отчеты.
- Управлять пользователями (только администратор).

Диаграмма вариантов использования представлена в файле:
- `docs/diagrams/use_case.puml`.

## 2 Проектирование и разработка программного продукта

### 2.1 Обоснование выбора программных средств реализации программного продукта

Для реализации выбраны следующие технологии:
- **Язык и платформа:** C# / .NET (Windows Forms).
- **СУБД:** Microsoft SQL Server.
- **Доступ к данным:** ADO.NET (`System.Data.SqlClient`).
- **Среда разработки:** Visual Studio.

Обоснование выбора:
- удобная реализация настольного клиентского приложения с формами;
- надежная интеграция с SQL Server;
- широкая поддержка в учебных и производственных проектах;
- возможность быстрого построения CRUD-интерфейсов и отчетных модулей.

### 2.2 Проектирование и создание базы данных

В базе данных используются основные таблицы:
1. **Users** — учетные записи сотрудников.
2. **Clients** — клиенты проката.
3. **Instruments** — музыкальные инструменты.
4. **Rentals** — факты аренды.
5. **Contracts** — договоры аренды.
6. **Payments** — платежи по аренде.

Логические связи:
- `Rentals.ClientID -> Clients.ClientID` (многие к одному);
- `Rentals.InstrumentID -> Instruments.InstrumentID` (многие к одному);
- `Contracts.RentalID -> Rentals.RentalID` (один к одному/один ко многим в зависимости от политики);
- `Payments.RentalID -> Rentals.RentalID` (многие к одному);
- `Payments.ReceivedBy -> Users.UserID` (многие к одному).

Правила целостности:
- инструмент со статусом `Rented` недоступен для новых аренд;
- аренда закрывается при возврате инструмента и переводе статуса в `Completed`;
- сумма платежа не должна превышать текущую задолженность.

ER-диаграмма представлена в файле:
- `docs/diagrams/erd.puml`.

### 2.3 Разработка клиентского программного обеспечения

Клиентское приложение организовано в виде набора форм:
- `LoginForm` — авторизация и переход к регистрации клиента;
- `MainForm` — главное меню с модулями системы;
- `InstrumentsForm` — учет и поиск инструментов;
- `ClientsForm` и `ClientRegistrationForm` — управление клиентской базой;
- `RentalsForm` и `ExtendRentalForm` — аренды, продление и завершение;
- `PaymentsForm` — регистрация оплат;
- `ContractsForm` — просмотр договоров;
- `ReportsForm` — аналитическая отчетность;
- `UserRegistrationForm` и `ChangePasswordForm` — администрирование пользователей и безопасность.

Особенности реализации:
- централизованная работа с БД через `DatabaseHelper`;
- хэширование паролей через `SecurityHelper`;
- хранение состояния текущего пользователя в `UserSession`;
- разграничение доступа по роли (модуль пользователей доступен только администратору).

## 3 Тестирование программного продукта

### 3.1 Методы тестирования программного продукта

Применены следующие методы:
1. **Модульное/компонентное тестирование вручную** (проверка отдельных форм и операций).
2. **Интеграционное тестирование** (цепочка «аренда -> договор -> платеж -> отчет»).
3. **Функциональное тестирование** по пользовательским сценариям.
4. **Негативное тестирование** (пустые поля, некорректные суммы, недопустимые статусы).

### 3.2 Организация процесса тестирования

Примеры тестовых сценариев:
1. Вход с корректным/некорректным логином и паролем.
2. Создание клиента с уникальным телефоном и e-mail.
3. Добавление инструмента и проверка его отображения в списке.
4. Создание аренды только для доступного инструмента.
5. Автоперевод статуса инструмента в `Rented` при создании аренды.
6. Завершение аренды с возвратом инструмента и статусом `Available`.
7. Проведение платежа в пределах задолженности.
8. Построение отчетов по доходам и задолженностям.

Критерии успешного тестирования:
- корректное выполнение бизнес-правил;
- отсутствие критических ошибок интерфейса и сохранения данных;
- воспроизводимость результатов отчетности на одинаковом наборе данных.

## 4 Подготовка документации

### 4.1 Руководство пользователя

1. Запустить приложение и пройти авторизацию.
2. В главном меню выбрать нужный модуль (Инструменты, Клиенты, Аренды, Платежи, Договоры, Отчеты).
3. Для создания аренды:
   - выбрать клиента;
   - выбрать доступный инструмент;
   - указать даты и депозит;
   - подтвердить операцию.
4. Для регистрации оплаты:
   - открыть модуль «Платежи»;
   - выбрать активную аренду;
   - ввести сумму и способ оплаты;
   - сохранить платеж.
5. Для получения аналитики:
   - открыть модуль «Отчеты»;
   - выбрать тип отчета и период;
   - просмотреть таблицу результата.
6. Администратор может открывать модуль пользователей и управлять учетными записями.

## ЗАКЛЮЧЕНИЕ

В ходе работы разработан программный продукт для автоматизации процессов аренды музыкальных инструментов. Реализованы ключевые функции: учет инвентаря, управление клиентами, оформление и сопровождение аренд, регистрация договоров и платежей, формирование отчетов.

Полученное решение позволяет сократить время операций, повысить качество учета и снизить вероятность ошибок, связанных с ручной обработкой данных. Система может быть расширена дополнительными модулями (уведомления, онлайн-бронирование, интеграция с платежными сервисами).
